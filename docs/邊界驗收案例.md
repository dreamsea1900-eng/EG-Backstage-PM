# Prototype Boundary 驗收案例

以下案例用來人工驗收 Agent 是否遵守通用邊界。

## 案例一：只有業務流程

輸入：「客服可編輯會員姓名、電話與 VIP，成功寫入歷程。」

預期：

- 直接製作可展示的會員編輯 prototype。
- 依既有後台模式使用詳情摘要＋適合欄位量的表單版型。
- 成功結果可表達「已記錄修改」，不要求 API 或歷程資料結構。
- 未要求查看歷程，因此不新增歷程按鈕或歷程頁。

## 案例二：既有頁截圖加一項修改

輸入：會員詳情頁截圖＋「在現有銀行帳號編輯 Modal 增加圖片上傳」。

預期：

- 保留現有頁面與 Modal 結構。
- 增加圖片上傳的展示欄位。
- 圖片數量、格式未定時採中性展示，不宣稱是正式限制。

## 案例三：泛稱錯誤處理

輸入：「儲存失敗顯示對應錯誤。」

預期：

- 不自行建立 success/error/network 三分支 Demo Radio。
- 依既有後台回饋慣例使用單一 error message／toast 展示，不要求錯誤碼。

## 案例四：明確探索

輸入：「目前沒有畫面，請幫我提出三種會員編輯方案。」

預期：

- 進入概念探索。
- 方案全部標記為未核准提案。
- PM 選定方案後即可製作，不要求補 API 或工程規格。

## 案例五：黃金範例有額外功能

輸入規格只有表格顯示，examples 另有搜尋、排序與新增 Modal。

預期：

- 只製作表格顯示。
- 可沿用拆檔與元件註解深度。
- 不因 examples 而繼承搜尋、排序、Modal、toast 或 mock 分支。

## 案例六：沒有 UI 規格

輸入：「做一個可依帳號與狀態查會員、點進去看基本資料的原型。」

預期：

- 不要求 PM 指定 Card、欄數、按鈕位置或 API。
- 查詢頁採既有搜尋 Card＋結果 Card＋Table。
- 詳情採摘要 Card＋資訊區塊。
- 不自行增加日期篩選、匯出、批次操作、權限或交易功能。

## 案例七：交易只有業務範疇

輸入：「交易包含入款、出款與額度異動。」

預期：

- 若做成可提交 Modal，依既有會員錢包模式至少呈現類型、金額與備註。
- 金額與備註記為展示假設，不宣稱是完整正式規格。
- 不得只選類型就顯示交易成功。
- 不增加付款方式、優惠、審核、回滾或報表入口。

## 案例八：後台框架未提供導覽

輸入：「做一個會員資料編輯頁。」

預期：

- 可使用 EG Header、Sider 與 Content 的視覺外殼。
- Sider 只顯示目前項目或省略。
- 不新增「會員查詢」、返回按鈕、麵包屑目的地或其他未提供入口。

## 案例九：背景副作用

輸入：「成功後寫入修改歷程與交易報表。」

預期：

- 不要求 API，也不新增歷程或報表入口。
- 不自動顯示「已寫入報表」提示；這是背景副作用。
- 若另有會影響客服當下決策的規則，才依既有 Alert 模式呈現。
