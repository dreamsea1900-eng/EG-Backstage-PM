# Prototype Boundary

目的：讓 PM 能快速展示已經想好的功能與概念，同時避免 Agent 加入奇怪的產品邏輯。
本 skill 不是需求稽核、API 對齊或工程驗收流程。

## 1. 開始前

完整讀取 [references/evidence-rules.md](references/evidence-rules.md)，再分析 PM 的目標。
新頁複製 [assets/scope-template.md](assets/scope-template.md) 為 `<頁面名>/SCOPE.md`；
它是 Agent 自用的簡短防幻想清單，不是要求 PM 簽核的規格報告。

## 2. 選擇模式

- **原型製作模式（預設）**：實作 PM 已描述的功能與想法，呈現方式依既有介面慣例補齊。
- **概念探索模式**：只有使用者明確要求「發想、提案、探索、提供方案」時啟用。

概念探索結果必須獨立標成「未核准提案」，不得直接寫入正式 prototype、`SCOPE.md`
的核准範圍，或當成後續輪次的既定事實。

## 3. 建立簡短邊界

只記錄：

- PM 想展示的核心功能與資料。
- PM 已指定的操作或狀態。
- Agent 為了呈現而採用的既有 EG 版型。
- 明確不加入的產品邏輯。

不逐欄建立證據矩陣，不要求 PM 確認 API、資料契約或所有例外分支。

## 4. 何時可以自行補齊

PM 已說明頁面目的與要展示的功能時，直接開始。未指定的呈現細節，依
`../antd-static-layout/references/eg-interface-patterns.md` 選擇最接近的既有版型，例如：

- 查詢條件＋結果表格使用查詢／列表頁。
- 少量既有資料編輯可使用既有 Modal 表單模式。
- 大量欄位或獨立任務使用全頁表單。
- 會員資訊與操作使用摘要 Card＋資訊區塊。

這些是呈現選擇，不是新增產品功能，也不需要 PM 先補 UI 規格。

只有以下情況才暫停並追問一個最小問題：

- 輸入互相矛盾，兩種解讀會改變核心功能。
- 無法判斷要做前台或後台。
- 無法判斷是修改哪個既有成果，且選錯會覆蓋內容。

## 5. 製作限制

- 允許依既有 EG 慣例補全版型、元件、間距、欄位排列、操作位置與 responsive 呈現。
- PM 提到的功能、欄位與想法可直接進 prototype，不需 API 或正式驗收條件佐證。
- 套用「最小完整操作」：只要介面提供可提交的動作，就必須具備讓該動作在畫面上成立的
  最少輸入與回饋。必要欄位未明說時，先從 EG 同類既有介面取最小集合，並在
  `SCOPE.md` 標成展示假設；不能做成無內容卻直接成功的假操作。
- 若沒有足以判斷最小輸入的既有模式，保留為靜態概念或停用操作，不宣稱可提交成功。
- 不新增 PM 沒提到的產品能力，例如匯出、批次操作、審核、歷程入口、權限管理、
  自動通知、補償或重試。
- 版型外殼不能創造產品入口：沒有輸入或既有畫面依據時，不新增側欄項目、麵包屑目的地、
  返回按鈕或其他看似可導覽的控制項。
- 不因規格提到「錯誤」「歷程」「紀錄」就自動建立對應頁面或入口。
- 背景副作用如寫入 Log、歷程、報表、回滾與補償不自動顯示成 Alert、說明或成功訊息；
  只有會影響操作者當下判斷的規則才映射到 UI。
- 可以建立足以展示畫面的合成資料；不得讓合成資料暗示額外產品規則。
- 只實作展示想法所需的最短互動，不模擬真實 API、交易一致性、回滾或工程例外。

## 6. 確認與交付

輸入足以判斷目標時直接製作，不先交付長篇報告或要求 PM 核准 `SCOPE.md`。

完成後只需簡短說明：

- 做了哪些可展示內容。
- 使用哪種既有 EG 版型。
- 哪些容易幻想的功能刻意沒有加入。

`SCOPE.md` 隨頁保存上述簡短邊界，供後續 Agent 修改時延續，不是 PM 的工程文件。
